THE PROBLEM

群聊通知，淹没在消息洪流里

大学生同时身处课程群、社团群、宿舍群、班级群，重要通知和闲聊混在一起——漏看、重复、过期、冲突，四个痛点反复发生。

📬

消息过载

通知被海量闲聊淹没，爬楼翻聊天记录才能找到关键信息

🔁

跨群重复

同一条通知被转发到多个群，反复打扰，效率低下

📝

通知变更

改期、换地点的消息淹没在后续消息里，看到的还是旧信息

⚡

信息冲突

不同群传来不一致的时间地点，不知道该信哪个

PRODUCT FLOW

从群聊消息到日历日程的完整闭环

Agent 自动监听多群消息，识别通知后跨群去重汇总，检测变更与冲突，经用户确认后通过 Tool Calling 写入日历。

CORE DESIGN

四个核心设计

双引擎识别保障可用性、变更检测解决信息过期、跨群去重减少打扰、Human-in-the-loop 守住执行底线。

01

双引擎识别层

规则引擎（零成本零延迟）兜底 + 可插拔 LLM（DeepSeek 等）处理模糊自然表述，LLM 失败自动回退规则引擎。

  • 规则引擎：关键词 + 正则，覆盖规范表述
  • LLM 输出归一化时间（如 2026-05-28 15:00），使相对时间可参与比对
  • OpenAI 兼容协议，DeepSeek / 智谱 GLM / 通义均可接入
可插拔 · 降级策略
02

通知变更与冲突检测

同一事件时间不同时触发变更流程，确认后按 UID 原位改写日历（非追加）；跨群时间矛盾则生成高风险卡片，必须人工裁决。

  • 操作词剥离（改期/变更/推迟）+ 模糊匹配解决表述不一致
  • 变更 → 新旧时间对比卡片 → 原位改写日历事件
  • 冲突 → 高风险提醒，Agent 不自动执行
UID 原位改写
03

跨群去重与消息汇总

同一通知被多个群转发时，自动判定为同一事件并入同一张待确认卡片，卡片附带全部消息原文（群名 + 发送人 + 原文）。

  • 不重复打扰，一张卡片汇总所有来源
  • 确认的是第一手信息，可溯源
  • 支持宿舍群、社团群、班级群等多场景
多群 · 可溯源
04

严格 Human-in-the-loop

任何写日历动作（新增 / 变更）都发生在用户确认之后；拒绝则完全不碰日历。Tool Calling 的执行结果真实写入 .ics 文件。

  • 确认卡片附消息原文，确保决策有据可查
  • create_calendar_event / update_calendar_event 真实执行
  • 支持 webcal 订阅，改期后手机日历自动同步
执行与展示解耦

DEMO WALKTHROUGH

演示流程

从发送通知到日历写入，四个步骤展示完整产品闭环。

1

发送通知

在模拟群聊中发送一条通知消息，Agent 自动识别事件名、时间、地点。

「数据结构期末考试定在6月10日 14:00，地点紫金港东1楼101」
2

跨群去重

同一通知被转发到宿舍群，Agent 自动判定为同一事件，并入同一张卡片。

宿舍群转发了同一条考试通知 → 合并到已有卡片
3

确认执行

卡片附消息原文，用户确认后 Agent 调用 Tool Calling 写入 calendar.ics。

✓ 确认执行 → create_calendar_event(title, start, location)
4

变更与同步

发一条改期通知，Agent 检测到变更，确认后按 UID 原位改写日历，手机日历自动同步。

「考试改到6月12日 14:00」→ update_calendar_event → 月历自动更新
